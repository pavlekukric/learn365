# Backend Strategy

The design document for the Learn365 backend. **Revised 2026-09-27** when Phase 8 started: the backend is a set of Next.js route handlers inside `apps/web`, backed by Postgres in the same Docker Compose project on the owner's VPS. The previous version of this file described a separate .NET 9 Web API on Azure; that plan is superseded and survives only in git history (`git show a34dd32:docs/BACKEND_STRATEGY.md`).

The concrete bundle for the first backend phase — locked decisions, file list, API contract, owner steps, gates — is [`PHASE_8_PLAN.md`](./PHASE_8_PLAN.md). This document keeps the longer-lived shape: why the backend exists, what it owns, and what stays the same on the client.

---

## 1. Role

The backend exists to let **progress belong to someone**: read on the laptop, continue on the phone, survive a cleared browser. Concretely:

- **Accounts** — Google sign-in only. No passwords to store, reset or leak.
- **Cloud progress** — completed lessons, last opened lesson, bookmarks, per course.
- **Account deletion** — one action, everything cascades.

Not in scope, and not planned unless explicitly added: payments, social features, analytics ingestion, content delivery from the server (lessons stay in the client bundle via `@learn365/content`), CMS.

---

## 2. Tech stack

| Layer | Choice |
|---|---|
| Runtime | Next.js 15 App Router **route handlers** under `apps/web/app/api/**`; server modules under `apps/web/lib/server/**` guarded by the `server-only` package |
| Database | **PostgreSQL 17** (`postgres:17-alpine`) as the `db` service of the `learn365` compose project on the Hetzner VPS; named volume; no published port |
| Data access | **Drizzle ORM** + `postgres` (postgres.js) driver; SQL migrations generated by `drizzle-kit`, committed, applied at server start from `instrumentation.ts` |
| Local dev / tests | **PGlite** (`@electric-sql/pglite`) through `drizzle-orm/pglite`, selected by the `pglite://` URL scheme — no Docker or Postgres install needed on the laptop; Vitest runs the repository layer against real SQL in memory |
| Auth | **Google OAuth 2.0 (authorization code + PKCE)** via `arctic`; sessions in our own `sessions` table; one `HttpOnly` cookie; `Origin` check on every mutating route |
| Hosting | Same image, same pipeline (`docs/DEPLOY.md`): GitHub Actions builds the image, `deploy.sh` rolls it out; secrets only in `/srv/learn365/.env` |
| Backups | Nightly `pg_dump -Fc` on the box, 14-day retention (`deploy/backup.sh` + one cron line); off-box copy is a follow-up |

Why this and not a separate API: one deployable and one PR surface; the content package is already on the server, so lesson ids are validated without duplicating data; the box is shared with Računi's SQL Server and a second database engine plus a second app runtime would be the wrong use of 4 GB.

---

## 3. Repository placement

```
apps/web/
├─ app/api/                      # route handlers (health, auth, me, progress, bookmarks)
├─ lib/server/                   # server-only: env, db (schema, client, migrations), auth, progress, bookmarks
├─ lib/auth/                     # client: AuthProvider, sign-in prompt state
├─ lib/sync/                     # client: ProgressSync, BookmarkSync
└─ instrumentation.ts            # runs migrations once at server start (nodejs runtime, only if DATABASE_URL is set)
```

There is no `apps/api`. `packages/core` stays React-free and backend-free: it gains pure merge helpers and one `replace*` action per store, nothing that knows about HTTP.

---

## 4. API surface

All under `/api`, JSON, dynamic. Auth-off (no secrets configured) → `/api/me` answers `{ enabled: false }` and everything else under `/api/auth`, `/api/me/*` is 404.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/health` | `{ ok, auth, db: 'ok' \| 'off' \| 'error' }` — the image healthcheck stays `GET /` so reading never depends on the database |
| `GET` | `/api/auth/google` | Start the Google flow (state + PKCE cookies), `?return_to=` same-origin path |
| `GET` | `/api/auth/google/callback` | Exchange the code, upsert the user, create the session, redirect |
| `POST` | `/api/auth/signout` | Delete the session, clear the cookie |
| `GET` / `DELETE` | `/api/me` | Current user; delete the account (cascades) |
| `GET` / `PATCH` | `/api/me/progress` | Course snapshot; apply `{ complete[], uncomplete[], lastOpenedLessonId }` |
| `POST` | `/api/me/progress/sync` | Merge a local snapshot into the account, return the canonical state |
| `GET` / `PATCH` | `/api/me/bookmarks` | Course bookmarks; apply `{ add[], remove[] }` |
| `POST` | `/api/me/bookmarks/sync` | Merge local bookmarks, return canonical |

Wire shapes mirror `docs/CONTENT_MODEL.md` → `UserProgress` field for field: `{ courseId, completedLessonIds, lastOpenedLessonId, updatedAt }`.

## 5. Authentication

- Google is the only provider; scopes `openid email profile`; identity key is the Google `sub`. We keep `email`, `name`, `picture` for the account page and the TopBar mark. No Google access or refresh tokens are stored.
- Session token: 32 random bytes, base64url, only its SHA-256 in `sessions.id`; 30 days, sliding renewal under 15 days left. Cookie `l365_session`: `HttpOnly`, `SameSite=Lax`, `Secure` on https, `Path=/`.
- CSRF: `SameSite=Lax` plus an `Origin === APP_URL` check on `POST` / `PATCH` / `DELETE`. `return_to` is accepted only as a same-origin relative path.
- ID token checks: `iss`, `aud`, `exp`, `email_verified`. The token is received directly from Google's token endpoint over TLS; signature verification is not required for that path.
- Sign-out clears the server session, then the client clears both local stores and the cloud marker. Deletion removes the user row; every other row cascades.

## 6. Database schema

```
users               id uuid pk, google_sub text unique, email text, name text, picture_url text,
                    created_at timestamptz, last_seen_at timestamptz
sessions            id text pk (sha256 of the cookie token), user_id uuid fk cascade,
                    expires_at timestamptz, created_at timestamptz
course_progress     user_id fk cascade, course_id text, last_opened_lesson_id text null,
                    updated_at timestamptz                       pk (user_id, course_id)
lesson_completions  user_id fk cascade, course_id text, lesson_id text, completed_at timestamptz
                                                                 pk (user_id, course_id, lesson_id)
bookmarks           user_id fk cascade, course_id text, lesson_id text, created_at timestamptz
                                                                 pk (user_id, course_id, lesson_id)
```

Content (`Course` / `Era` / `Section` / `Lesson`) does **not** live in SQL. Ids are the stable content strings; the server validates them against `@learn365/content` and drops unknown ones rather than failing a sync.

## 7. Client integration

The `localStorage`-backed stores in `@learn365/core` stay exactly as they are — they are what every surface renders from. Two small additions sit beside them:

- **Pure helpers + one action per store** in `@learn365/core`: `mergeCourseProgress` / `mergeCourseBookmarks` and `replaceCourseProgress` / `replaceCourseBookmarks` (apply a server snapshot wholesale).
- **Sync components** in `apps/web/lib/sync/` (`ProgressSync`, `BookmarkSync`), mounted in the providers, active only while signed in:
  1. first time this browser sees this user → `POST …/sync` with the local snapshot, replace local with the merged result (this is how anonymous progress migrates);
  2. every later page load → `GET`, replace local with the server state (server authoritative across devices);
  3. every local change → diffed, coalesced, sent as a `PATCH` delta with one retry; snapshot application never echoes back as a delta.

The UI does not know whether it is signed in beyond the TopBar mark, the account page and the one inline ask after the second completed lesson.

---

## 8. Migration story — local-only to cloud

1. The reader signs in for the first time on a browser that already holds progress.
2. `ProgressSync` sends the local snapshot to `POST /api/me/progress/sync`.
3. The server unions `completedLessonIds`, takes `lastOpenedLessonId` from the later `updatedAt`, writes, and returns the canonical state with its own `updatedAt`.
4. The client replaces local state with the response and writes the cloud marker (`learn365:cloud:v1 = { userId }`) so the union runs once per (browser, user).
5. From then on the server is authoritative on load; deltas flow up as they happen.

Un-completion is exact while online (delta), and replaces local on the next load elsewhere. Known v1 limitation: a delta that fails and is not retried before the tab closes is lost at the next load (no persistent outbox).

## 9. Hosting, environment, operations

- Runtime env in `/srv/learn365/.env` only: `DATABASE_URL`, `APP_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `POSTGRES_PASSWORD` (+ `IMAGE_TAG`). Never in the image, never in the repo.
- `authEnabled` is derived at request time from those four; without them the app is exactly the pre-Phase-8 app (CI, Playwright, the dark deploy).
- `db` container: `mem_limit 256m`, `shared_buffers 32MB`, `max_connections 20`; app pool max 5.
- Backups: `deploy/backup.sh` nightly from cron, `/srv/learn365/backups/`, 14 days. Restore = `pg_restore` into the `db` container; rehearsed once before declaring the phase done.
- Google Cloud: its own project (not Računi's), consent screen published to production with the non-sensitive scopes, privacy policy at `https://istorija365.com/privatnost`, redirect URI `https://istorija365.com/api/auth/google/callback`.
- Cloudflare: `www` → apex redirect so cookies and the OAuth origin live on one host.

## 10. What stays the same on the client (and why)

| Layer | Change required? |
|---|---|
| `@learn365/content` | None. Ids are already stable strings. |
| `@learn365/core` stores | Additive only: merge helpers + `replace*` actions. Persistence keys and shapes unchanged. |
| `@learn365/core` selectors | None. |
| `@learn365/ui` tokens | None. |
| `@learn365/ui-web` | Additive: `TopBar` `account` slot, `AccountMark`, `SignInPrompt`, `LessonReader` `signInPrompt?` prop, Footer `privacyHref`. |
| `apps/web` routes | New: `/prijava`, `/nalog`, `/privatnost`, `/api/**`. Existing routes unchanged and still static. |
| `apps/mobile` *(future)* | Same `/api/**` contract; the sync components port to React Native as is (fetch + store subscription). |

The property worth protecting: the v1 frontend becomes a v2 frontend by adding code, not by changing what is already there — and reading never depends on the backend being up.

## 11. Phases

Phase 8 ships as one PR (details in `PHASE_8_PLAN.md`): **8a** database + migrations + health; **8b** Google sign-in + pages + TopBar slot; **8c** progress sync + the ask after the second completion; **8d** bookmarks sync; **8e** docs. Every commit keeps auth-off behaviour identical, so the merge is a dark deploy; the owner turns the feature on by filling `.env`.

Later, if ever: off-box backups, a persistent client outbox, Apple sign-in (only if the native app ships to the App Store, where it is required next to Google), account export.

---

## 12. Open risks

- Own OAuth/session code — small, checklisted, tested; Auth.js v5 (JWT sessions) is the fallback behind the same `/api/me` contract.
- Two engines on one 4 GB box — hard memory caps; checked after the first day.
- Migrations at startup — additive only; a failure fails the healthcheck and the rollout, previous tag still runs.
- Backups on the same box — off-box copy needs an owner decision on destination.
- Privacy text not lawyer-reviewed — EU hosting, minimal data, deletion built in, the page says exactly that.
