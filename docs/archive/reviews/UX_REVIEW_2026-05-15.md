## How to read this

The app is genuinely in good shape — calm palette, editorial serif type, clean
architecture, real accessibility work. This review is not "it's broken", it is
"here is how to get from *very good* to *inevitable*", which is the bar set in
`CLAUDE.md`.

Findings are ordered by **impact on the felt experience**, not by effort.
Each item says **what**, **why it matters**, **where** (file), and a
**suggested direction** — kept deliberately simple, because the brief is
*simple as possible and premium*.

Nothing here has been implemented. This is a report for triage. Per the
project's "plan before code" rule, the recommendation is to pick the items you
want, and I'll write a phased plan for those before touching production code.

## Priority 1 — The lesson detail page

This is the screen you flagged ("Lepenski Vir … looks a bit chaotic"). I agree,
and it decomposes into five separate problems that happen to stack on one page.

### 1.1 The article floats in the middle of an oversized column

**What:** On desktop the layout is `[320px sidebar] [1fr reader]`. The reader
column adds `40px` of padding on each side, and *then* the article itself is
`max-width: 660px; margin: 0 auto` — centred. On a 1440px shell that leaves
roughly **220px of dead space on each side of the text**, and the text is not
visually anchored to anything.

**Why it matters:** This is almost certainly what you meant by "I would like to
have this positioned on the left". The eye expects the article to sit *next to*
the navigation rail, the way Pluralsight / Stripe docs / Linear docs do. Centred
text in a wide empty column reads as "unfinished template", not "premium".

**Where:** `packages/ui-web/src/lesson/LessonReader/LessonReader.module.css`
(`.reader { margin: 0 auto }`), `apps/web/.../LessonPageClient.module.css`
(`.readerColumn { padding: 0 var(--space-9) }`).

**Suggested direction:** Left-align the article against the sidebar — `.reader`
becomes `margin: 0` with a generous, fixed left gutter (e.g. `var(--space-10)`)
and the *right* side gets the breathing room. Keep the 660px reading measure;
just stop centring it. The page immediately feels composed instead of floating.

### 1.2 The sidebar header is overloaded — this is the "chaotic" feeling

**What:** Before you reach a single navigation row, the sidebar stacks **four**
distinct UI objects in its header:
1. `KURS` kicker + course title
2. progress bar + `1 / 365` count
3. the **"Idi na dan"** form (label + number input + "Idi" button)
4. *then* the era → section accordion tree begins

A form widget living inside a navigation rail is the single biggest source of
the "chaotic" read. It is a different interaction model (type + submit) wedged
between passive labels and a scannable tree.

**Where:** `packages/ui-web/src/course/CourseSidebar/CourseSidebar.tsx`,
`JumpToDay` is rendered inline in the header.

**Suggested direction (simplest first):**
- **Move `JumpToDay` out of the sidebar entirely.** It already exists on the
  Course overview page and the mobile drawer. The lesson sidebar's job is
  *browse*, not *search*. If a jump affordance is wanted here, demote it to a
  single small "Idi na dan →" link that focuses the input on the course page,
  or a tiny icon-button that expands on click — not a always-open form.
- Collapse the header to **two** things: course title + a thin progress line.
  That alone makes the rail read as a calm table of contents.

### 1.3 Progress is shown three times on one screen

**What:** On the lesson page the user's `X / 365` progress appears in:
- the **TopBar** capsule (sticky, always visible)
- the **CourseSidebar** header (right below the TopBar)
- the **LessonContextHeader** (mobile/≤1024px)

On desktop that's two identical progress bars stacked ~64px apart.

**Why it matters:** Repetition without new information is the enemy of "premium".
It also contributes directly to 1.2 — half the sidebar header is a duplicate of
the bar already pinned above it.

**Suggested direction:** The TopBar capsule is the canonical course-progress
indicator. **Drop the progress bar from the CourseSidebar header.** If the
sidebar wants progress at all, let it be per-era (the accordion counters
already do this) — that's information the TopBar *doesn't* carry.

### 1.4 Breadcrumbs are decorative — they don't navigate

**What:** `LessonPageClient` builds breadcrumbs as
`{ label: 'Početna', onClick: undefined }`, `{ label: courseTitle, onClick: undefined }`,
`{ label: era.title, onClick: undefined }`. The `Breadcrumbs` component renders
**any item without an `onClick` as a plain `<span>`** styled like the current
page. So "Početna", the course title, and the era are all unclickable text that
*looks* like a trail but goes nowhere.

**Why it matters:** A breadcrumb that doesn't navigate is worse than no
breadcrumb — it looks like a bug, and it wastes the one piece of obvious
"go up a level" affordance on the densest screen in the app.

**Where:** `apps/web/.../LessonPageClient.tsx` (breadcrumb construction),
`packages/ui-web/src/primitives/Breadcrumbs/Breadcrumbs.tsx`.

**Suggested direction:** Make breadcrumbs real links. The cleanest fix is to
let `BreadcrumbItem` take an optional `href` (rendered via `next/link`) the same
way the rest of `ui-web` switched from `onClick` to `href` in Phase 3 — this is
even noted as outstanding tech debt in `PROJECT_STATE.md`. Then: Početna → `/`,
course title → `/course/[id]`, era → era's first lesson. The last crumb stays a
span.

### 1.5 The full 8-era / 28-section tree is always mounted

**What:** The sidebar always renders all 8 `EraGroup` headers + all 28
`SectionAccordion` headers — ~36 rows of chrome — with only the *current*
section expanded.

**Why it matters:** It's a lot of visual texture for a "table of contents", and
it makes the rail feel like a wall. It's not wrong, but combined with 1.2 and
1.3 it's why the whole column reads as busy.

**Suggested direction:** Consider collapsing **eras** too, with only the current
era expanded by default (current section open inside it). The user lands on
"where am I", and the other 7 epochs are one calm click away. This is the
single change that would make the rail feel like Pluralsight's.

> **Net effect of 1.1–1.5:** the lesson page becomes — left-anchored article,
> a quiet two-line sidebar header, one progress indicator, working breadcrumbs,
> a tree that shows *where you are* rather than *everything there is*. That is
> the "simple and premium" you asked for, and none of it needs new visual design
> — it's mostly *removal*.

## Priority 2 — Content & information-architecture correctness

### 2.1 Era I claims years 600–1166 but contains a 9500 BCE lesson

**What:** Era I (`id: 'rani-srednji-vek'`, title *"Doseljavanje Slovena i rani
srednji vek"*, `yearStart: 600`) contains the section *"Praistorija i antika"*,
whose first lesson is **Lepenski Vir at year −7000** (`dateLabel: 'oko
9500–6000. p.n.e.'`).

**Why it matters — this is visible on the exact screen you flagged:**
- The **breadcrumb** for Lepenski Vir reads `… / Doseljavanje Slovena i rani
  srednji vek / Dan 001` — the wrong era for a Stone Age lesson.
- The **eyebrow** reads `DAN 001 · Rani srednji vek · 8 min · oko 9500 p.n.e.` —
  internally contradictory.
- The **timeline marker** interpolates year −7000 into an era ranged 600–1166,
  so it clamps to the era's left edge — technically defined behaviour, but the
  era label next to it is simply wrong.

**Where:** `packages/content/src/courses/istorija-srbije-365/eras.ts` (era I),
`sections.ts` (section `praistorija-i-antika` → `eraId: 'rani-srednji-vek'`),
`lessons/authored/praistorija-i-antika-001.ts`.

**Suggested direction (needs a product decision):** Three options, simplest to
most correct:
- **(a)** Rename Era I and widen its range to honestly cover "Praistorija →
  rani srednji vek" (e.g. `yearStart` far earlier, title *"Od praistorije do
  ranog srednjeg veka"*). Cheapest; keeps "8 eras locked".
- **(b)** Add a 9th era *"Praistorija i antika"*. Most historically honest, but
  breaks the "8 eras" decision and the 30+75+…=365 lesson maths.
- **(c)** Re-scope the *content* so day 1 isn't 9500 BCE. Least desirable —
  Lepenski Vir is a great opener.
  My recommendation is **(a)** — it's a data + copy change, no structural churn.

### 2.2 The placeholder-lesson experience

**What:** 359 of 365 lessons are stubs. Clicking almost anything in the sidebar
or timeline lands on the "Lekcija se uskoro objavljuje" card. The sidebar gives
**no visual signal** of which 6 lessons are actually readable.

**Why it matters:** A premium product shouldn't let the user repeatedly walk
into empty rooms with no warning. Right now exploration is mostly disappointment.

**Suggested direction (v1-appropriate, no new content needed):**
- In `LessonNavItem`, render placeholder lessons in a dimmed/`--faint` state
  with no completion dot — so the 6 real lessons visually stand out as the
  "available" ones.
- Optionally, the authored days (1, 7, 31, 106, 200, 305) could get a tiny
  "dostupno" affordance. The honest framing — "6 lekcija spremno, ostalo
  uskoro" — is more premium than silent dead ends.

### 2.3 The day identifier has three formats

**What:** `Dan 001` (breadcrumb), `DAN 001 / 365` (context header &
CourseProgress), `D001` (sidebar `LessonNavItem` & accordion ranges). Three
spellings of the same concept on screens the user moves between.

**Suggested direction:** Pick one. `DAN 001` for prose/headers, `D001` only for
the tight tabular sidebar rows is *defensible* — but `Dan 001` vs `DAN 001`
(breadcrumb vs header) is just inconsistent. Normalise to `DAN 001` everywhere
except the compact `D001` tabular column.

## Priority 3 — Home & Course overview

### 3.1 The hero says the same thing twice

**What:** The hero stacks: eyebrow → display title → **`course.subtitle` as a
lede** → **`HERO_DESCRIPTION` as a paragraph** → CTA. The subtitle and the
description are both "what this course is" copy, back to back.

**Why it matters:** Two intro paragraphs before the CTA dilutes the hero. The
most premium heroes are *one* confident line, then the action.

**Where:** `apps/web/app/page.tsx`.

**Suggested direction:** Keep **one**. Either the poetic `course.subtitle` *or*
the warmer `HERO_DESCRIPTION` — not both. Recommend keeping `HERO_DESCRIPTION`
(it was written specifically for Home) and dropping the subtitle lede here.

### 3.2 The hero backdrop image is doing a lot of work

**What:** `.heroBackdrop` is a 4-layer composite (CSS wash + image +
`mix-blend-mode: multiply` + cream overlay + mask gradient), with a separate
focal-point override on mobile. It's clever, but it's fragile — the kind of
thing that looks great on one viewport and muddy on another.

**Suggested direction:** Worth a deliberate visual QA pass at 360 / 768 / 1280 /
1920. If it doesn't read as crisp and intentional at *all four*, the
pure-CSS-wash fallback (already built in via `--hero-image: none`) is the more
premium choice. A clean wash beats a muddy photo.

### 3.3 Course overview vs sidebar — same tree, twice

**What:** The era → section → lesson accordion exists on the Course overview
page *and* in the lesson sidebar. Phase 6.5 deliberately made Home "visual" and
Course "functional", which is good — but the lesson sidebar then re-implements
the Course page's tree. Not a bug, but worth a conscious check that the two stay
in sync in behaviour (single-open vs multi-open: the Course page is single-open,
the sidebar is multi-open — minor inconsistency).

## Priority 4 — Smaller polish & correctness

- **`LessonReader` takes a `section` prop it doesn't use** (`void section;`).
  Dead prop — either render it (a section label above the title would actually
  *help* orient the reader) or drop it from the interface.
- **`section` is the obvious missing breadcrumb level.** The trail is
  Početna / Course / Era / Dan — but the *section* ("Praistorija i antika") is
  the one grouping the reader is actually inside. Consider Era → Section → Dan.
- **`CourseProgress` "current" row links to `#` when `currentHref` is null** but
  still looks clickable (`aria-disabled` doesn't stop the click). Minor, but a
  dead `#` link is a papercut.
- **Image blocks render as a diagonal-hatch placeholder.** Fine for stubs, but
  none of the 6 authored lessons should ship with hatch boxes in the final
  editorial pass — either source images or remove the image blocks from
  authored content.
- **`MarkAsCompletedButton` swaps icon side on toggle** (icon trails "Označi…",
  leads "Označeno…"). It's a nice touch, but verify it doesn't cause a layout
  jump — if it does, keep the icon on a fixed side.
- **Outstanding from `PROJECT_STATE.md`** and still relevant: screen-reader
  smoke pass, editorial review of the 6 authored lessons, and the
  `COMPONENT_LIBRARY.md` `onClick → href` revision (which item 1.4 above would
  finally force).

## Suggested sequencing

If you want to act on this, a clean order — each step is independently
shippable and each makes the next easier:

1. **Lesson page declutter** (1.1 + 1.2 + 1.3 + 1.5) — one focused pass, almost
   entirely *removal*. Biggest felt improvement, addresses your direct note.
2. **Breadcrumbs become real links** (1.4) — small, also clears Phase-3 tech debt.
3. **Era I content fix** (2.1) — data + copy, decision needed from you first.
4. **Placeholder lesson signalling** (2.2) — small `LessonNavItem` change.
5. **Hero tighten** (3.1) + **day-label normalise** (2.3) — quick polish.
6. **Hero image QA** (3.2) + **Priority 4 papercuts** — cleanup pass.

Steps 1–2 alone would resolve the "chaotic" read you described and are the
highest premium-per-effort. Tell me which of these you want and I'll write the
implementation plan for review before any code.
